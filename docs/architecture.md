# 시스템 아키텍처

## 전체 구조

```text
고객 / 운영자
    ↓
브라우저 (HTML / CSS / JavaScript)
    ↓ HTTP
Flask 요청 처리 계층
    ↓
서비스 계층 (요구조건 검증, 매칭, 대안, 배정, 시뮬레이션)
    ↓
데이터 접근 계층 (매개변수화 쿼리, 잠금, 저장 및 조회)
    ↓
MySQL (자원, 요청, 요구조건, 대안, 동의, 할당 이력)

pytest → 서비스 검증 및 MySQL 통합 검증
```

전체 흐름은 목표 구조이다. v0.1은 [6개 기본 테이블 명세](../database/erd.md), 가상 seed, 환경변수 기반 연결 및 테스트를 제공한다. v0.2-1은 터미널 하드웨어 조건 검사를, v0.2-2는 추가 테이블 2개와 트랜잭션 기반 배정·반환·이력 조회를 제공한다. 실제 DB 적용 버전은 DB별로 구분하며 웹 UI와 대안·동의 기능은 아직 구현하지 않았다.

## 계층별 책임

- 화면: 자원과 판단 결과를 표시하고 원본 요청 및 대안 수락·거절 의사를 전달한다.
- Flask 요청 처리: 입력 형식을 검증하고 서비스 호출 결과를 응답한다. 가용성 판단을 화면 코드에 맡기지 않는다.
- 서비스: 원본 조건 보존, 실행 가능성 판단, 대안 생성과 고객 동의 검증을 담당한다. 배정 서비스가 트랜잭션의 시작·커밋·롤백 경계를 조정한다.
- 데이터 접근: MySQL 조회·저장을 담당하며 배정 서비스의 동일 트랜잭션과 연결을 사용한다. 중간 단계에서 독자적으로 커밋하지 않는다.
- 시뮬레이션: 확정된 작업의 상태를 전환하고 종료 시 자원을 반환한다. 실제 GPU 연산이나 외부 학습 서비스를 호출하지 않는다.

## 개념적 데이터 구성

아래는 전체 목표의 논리적 책임 구분이다. v0.1에서는 고객, 서버, GPU 모델, 개별 GPU, 작업 요청, 원본 요구조건을 정의했고 v0.2-2에서 GPU 할당 이력과 ACTIVE/COMPLETED/FAILED 상태를 추가했다. 대안·고객 의사·자동 실행 시뮬레이션은 후속 구현 대상이다.

| 개념 | 책임 및 관계 |
| --- | --- |
| 고객 | 작업 요청의 주체이며 대안 수락·거절의 주체 |
| 서버 | 개별 GPU가 속한 장비와 서버 운영 상태 |
| GPU 모델 | 모델별 공통 정보 |
| 개별 GPU | 고유 식별자, 모델 참조, 서버 참조, 장비 상태 |
| 작업 요청 | 고객의 최초 요청과 작업 식별 정보 |
| 원본 요구조건 | 작업별 모델, 수량, 동일 서버 배치 등 변경하지 않는 조건 |
| 실행 대안 | 원본 작업에 연결된 변경 조건과 제안 근거; 여러 대안 가능 |
| 고객 의사 | 특정 대안에 대한 수락·거절과 의사 표시 시점 |
| GPU 할당 이력 | 작업과 실제 GPU의 관계, 활성 여부와 할당·해제 시점 |
| 작업 실행 상태 | 배정 후 시뮬레이션 진행과 종료 결과 |

실제 배정에는 원본 또는 수락한 대안 중 어떤 조건을 적용했는지 추적할 수 있어야 한다.
가용 수량은 별도 재고 숫자가 아니라 GPU·서버 상태 및 활성 할당에서 계산한 결과이다.

## 처리 흐름

1. 고객이 요청하면 최초 요청과 원본 요구조건을 저장한다.
2. 서버·GPU 상태 및 활성 할당을 조회해 실행 가능성을 판단한다. 조회 결과는 그 시점의 판단이다.
3. 원본 조건이 가능하면 원본 조건으로 배정을 시도한다. 불가능하면 변경 조건과 이유를 담은 대안을 저장·제시한다.
4. 대안 제시 단계에서는 GPU를 예약하거나 할당하지 않는다.
5. 고객이 대안을 수락하면 의사 기록을 남기고 수락한 조건으로 배정을 시도한다. 거절한 대안은 배정하지 않는다.
6. 배정 직전 자원 상태를 재검증하고 트랜잭션으로 확정한다. 실패하면 미배정 상태와 이유를 알린다.
7. 배정 성공 후 실행을 시뮬레이션하고 종료 시 할당을 해제한다.

고객의 수락 사실과 배정 성공은 별도 결과이다. 자원 부족으로 배정이 실패해도 수락 사실과 원본 요청은 유지하며, 새로운 조건을 적용하려면 새로운 동의를 받는다.

## 트랜잭션 및 동시성 설계 방향

MySQL InnoDB 트랜잭션을 사용하고, 모든 배정 경로가 동일한 잠금 순서를 따르도록 설계한다.
배정 시 작업 및 후보 GPU 행을 일정한 순서로 잠그고, 잠금 이후의 상태를 기준으로 서버 운영 가능 여부·장비 상태·활성 할당·요구조건을 다시 확인한다.
필요한 서버 상태도 같은 트랜잭션에서 보호하여 운영 상태 변경과의 경합을 처리한다.
필요 수량 전체를 확보한 경우에만 할당 기록과 작업 배정 상태를 함께 커밋한다. 부족하거나 오류가 나면 전체 롤백한다.

장비 상태 변경도 일관된 잠금 정책을 따라야 한다. 현재 배정·반환의 잠금 방식, 중복 방지 제약과 오류 시 롤백은 아래 v0.2-2 절에 구현 상태를 기록했다. 장비 운영 변경 API와 자동 재시도 정책은 후속 범위다.

## 디렉터리 책임

- `app/`: 현재 매칭·배정 CLI, 서비스와 데이터 접근 코드. Flask 앱·화면은 후속.
- `database/`: ERD, 기본 스키마·seed, 추가 마이그레이션과 DB 점검 도구.
- `tests/`: 서비스·CLI·마이그레이션 단위 테스트 및 실제 MySQL 통합 테스트.
- `docs/`: 요구사항, 구조와 설계 결정의 기준 문서.

설정은 환경변수로 전달하고 로컬 `.env`는 Git에서 제외한다. 테스트 DB는 개발 DB와 분리하고 실제 데이터가 담긴 덤프는 커밋하지 않는다.

## v0.1 구현 경계

`app.db`는 `.env`와 프로세스 환경변수로만 연결 정보를 받고 읽기 전용 연결 확인을 제공한다. `database.initialize`는 명시적 실행 시에만 빈 DB를 검사한 뒤 schema와 seed를 적용하며 기존 객체가 있으면 중단한다.
요청과 요구조건은 공유 PK로 최대 1:1을 강제한다. 두 행의 동시 저장과 정확히 한 요구조건 존재 보장은 후속 서비스 트랜잭션의 책임이다.
원본의 UPDATE/DELETE는 4개 트리거로 차단한다. v0.1만 적용된 DB는 할당 데이터가 없어 정상 장비 수만으로 최종 가용성을 판단하거나 배정을 확정할 수 없다. v0.2-2는 별도 allocations 헤더에 상태를 관리한다.

## v0.2-1 하드웨어 매칭 구조

```text
app.match_cli → services.hardware.check_hardware
                ├─ repositories.hardware.HardwareRepository → MySQL SELECT
                └─ services.hardware.evaluate_hardware → 불변 HardwareFeasibility
```

`app.matching`은 불변 요구조건·개별 GPU·서버별 수량·결과와 입력 오류를 정의한다.
저장소는 LEFT JOIN으로 원본 요청과 요구조건·모델을 조회하고, JOIN/WHERE로 요청 모델의 GPU와 서버 상태를 조회한다. 입력은 모두 `%s` 매개변수로 전달한다.
요구조건 없는 Job을 없는 Job과 구분하기 위해 LEFT JOIN을 사용한다. 제외 장비도 조회 결과에 남겨 설명과 장비 확인에 사용한다.

서비스는 요청 모델 일치, ONLINE 서버와 HEALTHY GPU 조건을 적용하고 서버 ID별로 집계한다.
수량 집계를 Python에서 한 번 수행해 개별 후보 목록과 서버별 수량의 기준을 공유한다. 별도 GROUP BY 조회를 추가하면 같은 자료를 중복 조회하므로 현재 두 SELECT 구조를 사용한다.
동일 서버 필수이면 서버별 최댓값, 분산 허용이면 총합으로 판단한다. GPU를 선택·예약·할당하지 않는다.

CLI는 별도 연결에서 REPEATABLE READ / WITH CONSISTENT SNAPSHOT / READ ONLY 트랜잭션을 시작한다.
모든 조회는 같은 스냅샷을 사용하며 성공·오류 모두 ROLLBACK 후 연결을 닫는다. 저장소·서비스는 트랜잭션을 시작하거나 종료하지 않으므로 후속 서비스의 기존 연결에서도 사용할 수 있다.
결과는 조회 시점의 하드웨어 조건만 설명하며 실제 실행 또는 배정을 보장하지 않는다.

## v0.2-2 배정·반환 구조

```text
app.allocation_cli
    ├─ available / history → AllocationRepository → 읽기 전용 스냅샷
    └─ allocate / complete / fail → AllocationService
          └─ READ COMMITTED 트랜잭션 → 잠금·재조회 → 전체 INSERT/UPDATE → COMMIT
                                     └─ 부족·충돌·오류 → 전체 ROLLBACK
```

`app.allocation`은 실제 배정·가용 조회 결과와 오류를 정의한다. `app.matching`과 v0.2-1의 하드웨어 판단은 유지한다.
`repositories/allocations.py`는 매개변수화 조회·행 잠금·INSERT·UPDATE·이력 조회를 담당하고 트랜잭션을 종료하지 않는다.
`services/allocations.py`는 트랜잭션의 시작·커밋·롤백, 잠금 순서, 정확한 GPU 조합 선택과 멱등성·무결성 검증을 담당한다. 기존 트랜잭션이 있는 연결은 변경하지 않고 거부한다.

잠금 순서는 **GPU 모델 → Job → 원본 요구조건 → 서버 ID 오름차순 → GPU ID 오름차순 → 할당 헤더 → 할당별 GPU 행**이다.
잠금 전 원본·할당 읽기는 잠글 대상을 찾는 데만 사용한다. 모델·Job 잠금 후 원본을 재조회하고 서버·GPU를 FOR UPDATE로 잠근 후 상태·미해제 할당을 다시 확인한다.
GPU의 모델·소속이 조회 도중 변경되어 잠근 서버 범위를 벗어나면 배정을 중단하고 재시도를 안내한다. 새로 추가된 GPU를 이번 배정에 반드시 포함하는 것은 보장하지 않는다.

현재는 같은 모델의 배정·반환을 모델 행 잠금으로 직렬화한다. 모델이 다르더라도 공유 서버는 같은 ID 순서로 잠근다. 처리량보다 명확한 정합성을 우선한 선택이며 후속으로 잠금 범위를 축소할 수 있다.
READ COMMITTED를 사용해 잠금 대기 이후 새로 커밋된 할당을 이전 스냅샷 때문에 놓치지 않는다. 잠금 시간 초과·교착상태 오류도 전체 롤백하며 자동 무한 재시도는 하지 않는다.

동일 서버 필수이면 수량을 충족하는 가장 작은 서버 ID에서, 분산 허용이면 `(server_id, gpu_id)` 순서로 필요한 개수만 선택한다. allocation_gpus에 GPU ID와 배정 당시 서버 ID를 기록한다.
배정 전 하드웨어 조건 충족만으로 성공을 반환하지 않는다. 현재 가용 조회도 조회 시점의 참고 결과이며 실제 배정에서 다시 검증한다.

배정 시각과 모든 assigned_at은 같은 UTC 시각을 사용한다. 반환 시 모든 released_at과 헤더 ended_at을 같은 UTC 시각으로 갱신하고 헤더 상태를 COMPLETED 또는 FAILED로 변경한다.
배정 또는 반환 중 한 SQL이라도 실패하면 전체를 롤백한다. 서비스는 이력을 DELETE하지 않는다.
통신 단절로 COMMIT 응답이 유실되면 서버의 커밋 여부가 불명확할 수 있다. 같은 Job으로 재조회·재호출해 기존 결과를 확인하며 새로운 중복 배정을 생성하지 않는다.

Generated Column은 다른 테이블의 상태를 참조하지 않는다. 헤더의 ACTIVE Job 키와 자식의 미해제 GPU 키를 각각 UNIQUE로 보호하고 두 테이블의 상태 전이는 서비스 트랜잭션으로 함께 처리한다.
지원하지 않는 직접 SQL 변경으로 상태가 어긋나면 서비스는 무결성 오류로 중단한다. 가용 조회는 ACTIVE 헤더 또는 미해제 자식이 있는 GPU를 보수적으로 제외한다.
일반 운영 계정에는 이력 DELETE 권한을 주지 않는 정책이 필요하다. 이번 작업에서 계정 권한이나 트리거는 변경하지 않았다.

마이그레이션·기존 복구 도구의 버전 처리와 DDL 부분 실패 복구는 [마이그레이션 안내](../database/migrations/README.md), 실제 결과는 [v0.2-2 검증 기록](v0.2-2-validation.md)을 따른다.

2026-11-08 기존 구현 검토와 재실행에서 전체 240개 및 실제 MySQL 83개 통과를 확인했다. 단일 연결 SQL 검증은 SAVEPOINT 외피를 사용하고, 동시성·CLI 6개는 실제 별도 연결과 커밋을 사용한다. 외피 없이 서비스의 실제 외부 트랜잭션을 사용한 부분 INSERT 실패·반환 실패 롤백도 별도로 확인했다.
개발 DB는 6개 테이블, 테스트 DB는 8개 테이블이며 이번에는 DDL 없이 검사했다. 배정 CLI의 기본 연결 대상은 개발 DB이므로 현재 배정 검증에는 `--test`를 명시해야 한다.
