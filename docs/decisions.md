# 설계 결정 기록

아래 원칙은 초기 설계의 기준이다. 요구사항을 바꾸는 경우에는 변경 이유와 영향을 이 문서에 함께 기록한다.
세부 테이블과 구현 방식은 후속 설계에서 확정하되 이 원칙을 만족해야 한다.

## 1. GPU는 개별 자원으로 관리한다

GPU마다 고유 식별자를 부여한다. 모델별 총수량만 관리하면 어떤 장비가 할당되었는지 알 수 없으므로, 개별 할당과 중복 배정 방지를 위해 실제 장비 단위로 관리한다.

## 2. 각 GPU의 모델, 소속 서버, 장비 상태를 관리한다

모델은 요청 적합성을, 서버는 배치 가능성을, 장비 상태는 운영 가능성을 판단하는 기준이다. 이를 구분하면 동일 모델이라도 고장 장비나 다른 서버의 GPU를 잘못 포함하는 것을 방지할 수 있다.

## 3. 가용 GPU 수량은 장비 상태와 할당 기록으로 계산한다

정상 장비이며 서버가 운영 가능하고 활성 할당이 없는 GPU를 계산한다. 가용 수량을 별도로 수정하면 실제 장비·할당과 숫자가 어긋날 수 있으므로 이를 파생 값으로 취급한다.

## 4. 고객의 최초 작업 요청은 변경하지 않고 보존한다

요청을 처음 받은 내용과 원본 조건을 유지한다. 대안이나 실행 결과가 생겨도 원본과 비교할 수 있어야 하며 고객 의사와 시스템 판단을 추적할 근거가 필요하다.

## 5. 작업별 요구조건은 별도로 관리한다

GPU 모델, 수량, 동일 서버 배치 여부 등의 조건을 작업 요청의 기본 정보와 구분한다. 구조화된 조건은 검증과 매칭에 사용하고, 원본 조건과 대안 조건을 혼동하지 않도록 연결 관계를 명확히 한다.

## 6. 고객 동의 없이 작업 조건을 변경하지 않는다

GPU 모델 변경이나 수량 축소, 배치 조건 완화는 작업 수행 의도에 영향을 줄 수 있다. 시스템이 조건을 임의로 바꾸지 않고, 고객이 승인한 조건만 배정 판단에 사용한다.

## 7. 최초 요청이 어려우면 실행 가능한 대안을 제시하고 동의를 받는다

대안에 원본과의 차이 및 제안 이유를 포함하고 고객의 수락·거절을 기록한다. 단순 실패 안내를 넘어 선택지를 제공하되 고객이 변경 내용을 이해하고 결정할 수 있어야 한다. 가능한 대안이 없을 수도 있으며 이때는 불가 사유를 제시한다.

## 8. 대안 제시 시 실제 GPU를 예약하지 않는다

제안은 생성 시점의 자원을 기준으로 한 가능성 안내이다. 고객이 검토 중인 여러 대안이 자원을 점유하면 다른 요청을 불필요하게 막을 수 있으므로 제안과 실제 할당을 분리한다.

## 9. 대안 수락 후 재검증하고 트랜잭션으로 배정을 확정한다

제안과 수락 사이에 자원 상태가 변할 수 있다. 수락 시 잠금과 재조회로 실제 가용성을 검증하고 필요한 GPU 전부를 원자적으로 확정하여 중복 배정 및 부분 배정을 방지한다. 자원이 부족하면 배정 실패를 알리고 새 대안은 별도 동의를 받는다. 원본 조건의 배정에도 동일한 재검증과 트랜잭션 원칙을 적용한다.

## 10. AI 학습과 GPU 연산은 시뮬레이션한다

실제 학습 인프라 구축 대신 관계형 데이터 모델, 무결성, 가용성 판단과 동시성 제어에 개발 범위를 집중한다. 실행 상태와 자원 반환을 시뮬레이션하여 장비 없이도 전체 업무 흐름을 검증한다.

## 초기 범위에 대한 추가 가정

첫 버전은 현재 시점의 즉시 배정을 대상으로 한다. 미래 예약, 대기열 최적화, 전력·냉각·가격 기반 최적화는 별도 요구사항과 데이터 모델을 합의한 후 확장한다. 이는 초기 구현 범위를 명확히 하기 위한 가정이며 고객의 요구조건을 임의로 완화하는 근거로 사용하지 않는다.

## v0.1 구체화 (2026-11-03)

기존 10개 원칙을 유지하며 아래 구현 선택을 추가했다.

- **MySQL 8.0.16 이상 / InnoDB**: CHECK가 실제 강제되는 버전을 사용하고 트랜잭션·참조 무결성을 확보한다. 연결은 strict SQL mode와 UTC 세션을 사용한다. [MySQL CHECK 문서](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)를 기준으로 한다.
- **공유 PK 요구조건**: `job_requirements.job_request_id`를 PK 겸 FK로 사용해 작업당 원본 요구조건이 중복되지 않도록 한다. DB는 1:0..1만 보장하므로 후속 등록 서비스가 요청·요구조건을 동일 트랜잭션으로 저장해야 한다. 원본은 모델 한 종류만 요구한다.
- **원본 UPDATE/DELETE 차단**: 두 원본 테이블에 총 4개 트리거를 두어 동의 없는 조건 변경과 이력 삭제를 차단한다. 실행 상태는 향후 별도 테이블에서 관리한다. 원본 보존 원칙을 DB에서도 강제하기 위한 선택이다. 따라서 제목 등 원본 부속 필드도 변경할 수 없다.
- **할당 상태 미도입**: 서버 ONLINE/MAINTENANCE/OFFLINE과 GPU HEALTHY/FAULTY/MAINTENANCE만 정의한다. 할당 여부나 가용 수량은 넣지 않는다. 할당 테이블 추가 전에는 가용성 판단을 완성하지 않는다.
- **참조 삭제 제한**: FK는 RESTRICT를 사용하고 연쇄 삭제를 피한다. 원본 요청과 실제 장비의 관계 이력을 보존하기 위한 선택이다.
- **빈 DB만 최초 적용**: 적용 도구는 기존 객체가 있으면 멈추며 seed는 일반 INSERT를 한 트랜잭션으로 실행한다. 충돌을 숨기는 IF NOT EXISTS, IGNORE, REPLACE, upsert를 피한다. DDL의 암묵적 커밋으로 일부 객체가 남으면 자동 삭제 없이 중단한다.
- **분리된 명시적 통합 테스트**: TEST_MYSQL_* 전체 설정과 `_test` 이름, 개발 DB와 다른 이름, `--run-mysql`을 요구한다. 테스트 데이터는 롤백하며 준비되지 않은 DB를 추측하거나 자동 생성하지 않는다.
- **직접 Connector 사용**: 현재 범위에는 ORM 없이 mysql-connector-python을 사용한다. SQL 제약과 트랜잭션 동작을 학습·검증하는 프로젝트 목적에 맞는 최소 연결 방식이다. [공식 연결 옵션](https://dev.mysql.com/doc/connectors/en/connector-python-connectargs.html)을 따른다.
