# 요구사항

## 범위와 사용자

고객은 AI 학습 작업을 요청하고 제안된 대안을 검토·수락합니다. 운영자는 서버 및 개별 GPU 정보와 운영 가능 상태를 관리합니다.
실제 AI 학습 실행, GPU 드라이버 제어, 과금 및 외부 클라우드 연동은 이번 프로젝트의 범위에서 제외합니다.
v0.4-2는 로컬 시연용 한국어 Flask 화면을 제공합니다. 실제 사용자 인증과 운영 배포는 후속 설계에서 구체화합니다.

## 승인된 상위 방향과 미구현 요구사항

[프로젝트 마스터 계획](PROJECT_MASTER_PLAN.md)은 기존 GPU 중심 v0.4-2의 최소 전체 시연을 먼저 완성한 뒤 GPU·CPU·RAM 복합 자원으로 확장하는 로드맵입니다. 현재 아래 FR·버전별 구현 기록의 범위는 변경하지 않습니다. 복합 자원 3개 테이블·원본 보호·레거시 정책·GPU당 CPU/RAM 단위·서버별 합계 잠금은 **M1에서 확정할 미구현 요구사항**으로, 본 문서의 기존 FR 완료 상태에 자동 포함되지 않습니다.

## 주요 기능

| ID | 기능 | 요구사항 |
| --- | --- | --- |
| FR-01 | 서버·GPU 관리 | GPU마다 고유 식별자, GPU 모델, 소속 서버, 장비 상태를 관리한다. 서버의 운영 가능 여부도 판단에 반영한다. |
| FR-02 | 가용 자원 조회 | 정상 장비 중 유효한 할당과 충돌하지 않는 GPU를 조회하고 수량을 계산한다. 가용 수량 자체를 별도의 원본 값으로 저장하지 않는다. |
| FR-03 | 작업 요청 저장 | 고객의 최초 요청을 보존하고 작업별 GPU 모델, 양의 정수 수량, 동일 서버 배치 여부 등의 요구조건을 별도로 관리한다. |
| FR-04 | 실행 가능성 판단 | 원본 요구조건과 장비·서버 상태 및 할당 내역을 비교하여 실행 가능 여부와 불가 사유를 제시한다. |
| FR-05 | 대안 제시 | 실행이 어려우면 모델·수량·배치 등의 변경 조건, 원본과의 차이, 제안 이유를 별도 대안으로 제시한다. 가능한 대안이 없으면 그 사유를 안내한다. |
| FR-06 | 고객 의사 기록 | 대안 수락·거절을 기록한다. 동의 전에는 변경 조건을 적용하지 않으며 원본을 덮어쓰지 않는다. |
| FR-07 | 배정 확정 | 원본 조건 또는 고객이 수락한 대안 조건을 기준으로 자원을 재조회하고, 트랜잭션으로 개별 GPU 할당을 확정한다. |
| FR-08 | 충돌 처리 | 재검증 중 자원이 부족해지면 전체 배정을 취소하고 재검토 또는 새 대안을 안내한다. 일부 GPU만 확정하지 않는다. |
| FR-09 | 실행 시뮬레이션 | 확정된 배정에 대해 실행·완료·실패를 시뮬레이션하고 종료 시 할당을 해제한다. 실제 학습이나 GPU 연산은 수행하지 않는다. |
| FR-10 | 이력 조회 | 원본 요청, 요구조건, 대안, 고객 동의, 할당과 실행 상태의 관계를 추적할 수 있다. |

## 데이터 및 배정 제약

- GPU 모델 정보와 개별 GPU 자원을 구분하고, 각 GPU의 소속 서버를 식별한다.
- 장비 상태와 작업 할당 상태는 서로 구분한다. 정상 장비라도 할당 중이면 중복 배정할 수 없다.
- 최초 요청과 원본 요구조건은 저장 후 수정하지 않는다. 조건 변경은 원본과 연결된 대안으로 표현한다.
- 동일 서버 배치를 요구하면 필요한 GPU 전부를 한 서버에서 확보해야 한다. 서버 간 수량 합산으로 충족 처리하지 않는다.
- 모델 변경, 수량 축소, 동일 서버 조건 완화 등을 자동 적용하지 않는다.
- 대안 생성·조회는 GPU 예약, 할당 기록 생성 또는 장비 상태 변경을 수행하지 않는다.
- 대안 수락은 자원 확보를 보장하지 않는다. 수락한 고객과 대상 작업·대안의 관계를 검증한 뒤 배정을 시도한다.
- 동시 요청에서 동일 GPU가 중복 배정되지 않도록 트랜잭션과 잠금 정책을 적용한다.
- 동일 요청의 반복 수락·확정 호출로 중복 할당이 생기지 않도록 상태와 기존 할당을 확인한다.
- 완료·실패로 할당을 해제해도 과거 할당 이력을 삭제하지 않는다.

## 초기 운영 범위

초기 버전은 현재 시점의 즉시 배정을 기준으로 한다. 미래 시간대 예약 및 작업 대기열 최적화는 후속 확장으로 둔다.
가용성 판단은 현재 서버 운영 상태, GPU 장비 상태와 활성 할당을 기준으로 한다. 전력·냉각·비용 등 추가 운영 조건은 데이터와 판단 기준을 정의한 후 확장한다.
상태 이름과 전이, 상세 필드 및 DB 제약의 구현 방식은 ERD 설계 단계에서 확정한다.

## 품질 요구사항

- MySQL의 참조 무결성과 트랜잭션을 활용해 데이터 일관성을 보장한다.
- 비밀번호 및 비밀키는 환경변수로 분리하고 저장소와 로그에 포함하지 않는다.
- 고객 입력은 서버에서 검증하고 DB 접근 시 매개변수화된 쿼리를 사용한다.
- 판단 로직은 화면과 분리하여 pytest로 검증할 수 있게 구성한다.
- 실제 고객 정보 대신 가상 데이터를 개발 및 테스트에 사용한다.

CLI의 고객 ID 일치 검사는 Job·제안의 업무 관계 검증이다. 로그인이나 사용자 본인 확인을 제공하지 않으며 실제 인증·접근 제어는 후속 웹 계층에서 구현해야 한다.

## 후속 구현의 검증 기준

1. 정상 GPU 4개 중 1개가 활성 할당 중이면 가용 수량은 3개이다. 고장·점검 장비는 제외한다.
2. 두 서버에 GPU가 각각 2개 있어도 동일 서버 GPU 4개 요청은 충족되지 않는다.
3. 대안을 생성한 전후의 GPU 가용 수량과 활성 할당은 동일하다.
4. 대안을 수락해도 원본 요청과 원본 요구조건은 변하지 않는다.
5. 제안 이후 다른 작업이 GPU를 사용하면 수락 시 재검증하고, 부족하면 할당 없이 종료한다.
6. 두 요청이 동시에 동일 GPU를 배정하려 해도 유효한 할당은 하나만 존재한다.
7. 배정 중 오류가 발생하면 일부 할당이나 성공 상태가 남지 않는다.
8. 동의 없는 조건 변경 및 반복 확정에 따른 중복 배정을 거부한다.

## v0.1 제공 범위

6개 기본 테이블, PK/FK/UNIQUE/CHECK, 서버·GPU 상태 및 원본 보존 트리거, 가상 seed, Mermaid ERD, 최소 연결 코드와 pytest를 제공한다.
요청당 원본 요구조건은 GPU 모델 한 종류와 수량·동일 서버 플래그 한 쌍으로 표현한다. 여러 GPU 모델을 한 작업에서 혼합 요구하는 기능은 후속 범위다.
요청과 요구조건의 정확히 1:1 저장, 매칭 판단, 대안, 고객 동의 및 할당 기록은 후속 서비스·스키마에서 구현한다. 전체 요구사항을 v0.1에서 모두 구현한 것으로 해석하지 않는다.

## v0.2-1 제공 범위

- 원본 Job ID로 GPU 모델·수량·동일 서버 요구조건과 개별 장비·서버 상태를 조회한다.
- 요청 모델 PK가 일치하고 GPU가 HEALTHY, 서버가 ONLINE인 장비만 후보로 인정한다.
- 동일 서버 필수이면 한 서버의 후보 수가 필요 수량 이상이어야 한다. 분산 허용이면 서버별 후보 수를 합산하며 한 서버만으로 충족해도 허용한다.
- 결과는 HARDWARE_FEASIBLE / HARDWARE_INSUFFICIENT로 구분하고 모델 장비 부재·수량 부족·동일 서버 부족을 설명한다. 한 요청에 여러 부족 사유가 함께 있을 수 있다.
- INVALID_JOB_ID / JOB_NOT_FOUND / MISSING_JOB_REQUIREMENT는 하드웨어 부족과 구분하는 오류다.
- 읽기 전용 하드웨어 검사만 구현한다. 할당·예약 정보가 없어 FR-02·FR-04의 최종 가용성을 구현한 것으로 해석하지 않는다. 실제 즉시 실행 가능 또는 배정 확정을 뜻하지 않는다.
- v0.1 스키마·트리거·seed는 유지한다. 할당·예약, 대안, 동의, 시간·완료 예측, 웹 UI와 학습 실행은 이번 범위에서 제외한다.

## v0.2-2 제공 범위

- 기존 6개 테이블을 변경하지 않고 버전별 마이그레이션으로 allocations / allocation_gpus를 추가한다.
- ONLINE + HEALTHY이고 미해제 자식 또는 ACTIVE 헤더로 점유되지 않은 GPU를 현재 가용 자원으로 조회한다. 하드웨어 판단 결과와 별도로 AVAILABLE / INSUFFICIENT_RESOURCES를 제공한다. 지원하지 않는 직접 SQL로 헤더·자식 상태가 어긋나도 보수적으로 제외한다.
- 원본 요구조건만 사용해 잠금 후 상태·활성 할당을 재조회하고 정확한 개별 GPU 조합을 기록한다. 필요 수량 전체를 확보한 경우에만 배정 트랜잭션을 커밋한다.
- 한 Job의 중복 ACTIVE 할당과 같은 GPU의 중복 미해제 할당은 Generated Column + UNIQUE로 DB에서도 거부한다.
- ACTIVE 배정의 완료·실행 실패 시 헤더의 COMPLETED / FAILED·종료 시각과 모든 GPU 해제 시각을 하나의 트랜잭션으로 기록한다. 이력은 유지하고 GPU를 재사용할 수 있다.
- 배정 전 자원 부족·중복 충돌·DB 오류는 전체 롤백하며 FAILED 실행 이력을 만들지 않는다. FAILED는 실제 배정이 확정된 후의 실행 실패를 의미한다.
- 같은 Job의 반복 배정은 기존 ACTIVE 또는 종료 결과를 반환한다. 완료 후 같은 Job을 자동 재시작하지 않는다. 명시적 재실행 정책은 후속 범위다. 같은 종료 상태의 반복 호출은 멱등적으로 처리하고 다른 종료 상태로 덮어쓰지 않는다.
- 개발 DB 마이그레이션은 별도 사용자 승인이 필요하다. 2026-11-08 승인 후 검증된 백업과 기존 마이그레이션 함수로 2개 테이블만 추가했다. 기능 검증은 개발 DB에서 읽기 전용, 배정·반환·동시성은 전용 테스트 DB에서 수행한다. 기존 행·4개 트리거는 보존한다.
- 고객 대안·동의·예약, 실제 학습, 시간 예측, Flask UI는 여전히 제외한다. 대안 생성 시 GPU를 미리 예약하지 않는 정책을 유지한다.

## v0.2-2 검증 상태 (2026-11-08)

전체 240개(로컬 157개 + 실제 MySQL 83개)를 직접 재실행해 통과했다. 실제 동시 배정, 동일 Job 멱등성, UNIQUE 거부, 수량 부족·부분 SQL 실패의 롤백, 완료·실패 후 반환·재사용·이력 보존을 검증했다. 기존 하드웨어 매칭도 유지된다.
FR-02·FR-04·FR-07·FR-08은 원본 조건에 대한 조회·배정 범위를 검증했다. FR-09는 CLI로 종료 상태를 전환하는 범위, FR-10은 GPU별 할당 이력 범위만 구현했다. FR-03의 등록 서비스, FR-05·FR-06의 대안·의사 기록, 자동 시뮬레이션과 화면은 후속이다.
최초 재검증은 개발 DB에 DDL을 적용하지 않고 테스트 DB의 8개 구성을 사용했다. 이후 사용자 승인에 따른 개발 DB 마이그레이션까지 완료했고 두 DB 모두 8개 테이블·4개 트리거·기존 seed를 유지한다. 적용 후에도 전체 240개·실제 MySQL 83개가 통과했다. 상세 증거와 남은 작업은 [검증 기록](v0.2-2-validation.md)을 따른다.

## v0.3-1 제공 범위 (2026-11-08)

- FR-05: 원본이 현재 가용성을 만족하면 제안하지 않는다. 같은 모델의 분산 배치와 수량 축소만 지원한다. 분산 배치는 원본이 동일 서버 필수이고 전체 미할당 수량은 충분할 때 원본 수량을 유지하며 배치를 완화한다. 수량 축소는 원본 배치를 유지한 채 가능한 최대 양의 수량을 원본보다 작게 제시한다.
- ONLINE 서버·HEALTHY GPU·미해제 또는 ACTIVE 할당 제외 정책은 기존 평가기를 재사용한다. 생성한 모든 대안의 수량·배치를 같은 평가기로 다시 확인한다. 가용 수량 0개, 원본과 동일한 조건, 수량 증가와 모델 대체 제안은 만들지 않는다.
- 분산 학습 지원과 수량 축소의 성능·시간·품질 영향은 확인되지 않았음을 저장·표시한다. 원본과 같은 학습 결과를 보장하지 않는다. 시간 연장·epoch 축소·성능 예측은 제외한다.
- FR-06: Proposal ID뿐 아니라 Job ID와 고객 ID를 검증한다. 한 제안에는 최초 ACCEPTED 또는 REJECTED만 기록하고 동일 요청은 ID·시각을 보존해 재응답한다. 반대 의사는 충돌이다. Job당 수락된 제안은 최대 하나이며 다른 제안의 거절은 보존할 수 있다.
- 같은 Job·모델·수량·배치 조건은 재등록하지 않는다. 거절된 제안을 재생성해 응답을 지우지 않는다. 자원 변화로 조건이 달라지면 새 제안을 만들고 과거 제안·응답을 유지한다.
- FR-10: 제안 상세와 원본 비교, Job별 제안·응답 이력 및 수락된 제안의 근거 ID를 조회한다. 서비스는 제안·응답을 UPDATE/DELETE하지 않는다.
- 제안 생성·조회·수락·거절은 GPU 할당, 장비·서버 상태 변경, 기존 GPU 반환을 수행하지 않는다. 제안 이후 가용성이 바뀌어도 고객 의사를 기록할 수 있으며 수락은 배정 성공을 보장하지 않는다. FR-07의 수락 대안 배정은 v0.3-2 범위다.
- 기존 8개 테이블과 원본 보호 트리거 4개는 유지한다. 테스트 DB에만 003으로 job_proposals / proposal_responses를 추가해 10개 테이블이 됐다. 개발 DB는 8개 상태를 유지하며 신규 적용은 별도 승인 이후다.

전체 **364개(로컬 230 + MySQL 134)**가 통과했고 기존 240개도 유지했다. 신규 124개는 대안·응답 단위 73개, 실제 MySQL 51개다. 실제 결과와 보존 증거는 [v0.3-1 검증 기록](v0.3-1-validation.md)을 따른다.

## v0.3-2 수락 대안의 실제 배정

- 원본 배정과 수락 대안 배정을 ORIGINAL / ACCEPTED_PROPOSAL로 구분한다. 대안 배정은 Job·Proposal·소유 고객·ACCEPTED 응답이 모두 일치해야 한다.
- 원본을 잠근 뒤 대안·응답을 재검증하고 현재 ONLINE 서버의 HEALTHY 미할당 GPU만 선택한다. 생성·수락은 예약이 아니다.
- 전체 수량 부족이나 SQL 실패는 헤더·GPU 연결·배정 근거를 모두 롤백한다. 같은 Job/GPU의 활성 중복은 기존 UNIQUE로 차단한다.
- 같은 Job·같은 근거 반복은 기존 ACTIVE/종료 결과를 재사용한다. 다른 근거는 명시적 충돌이다. Job 재실행 정책은 추가하지 않는다.
- 완료/실패 시 기존 반환 기능으로 GPU 전체를 해제한다. 원본·대안·수락·적용 조건·배정 당시 서버·배정/반환 시각을 보존한다.
- CLI: allocate, allocate-proposal, detail, job-history, history, complete, fail. 고객 ID는 인증이 아니다.
- 기존 364개를 유지하고 실제 Job 003 분산 4개/동일 서버 3개, Job 005 A100 2개 배정·반환을 검증한다.
- 개발 DB는 읽기 전용 8개를 유지한다. 004는 백업 및 기존 10개 정의·모든 행 검사 후 테스트 DB에만 적용한다.

## v0.4-1 신규 Job 등록·조회 구현

- 기존 고객·GPU 모델을 참조하는 신규 Job을 Python 서비스·CLI로 등록한다. 입력은 customer_id, title, original_request, gpu_model_id, gpu_count, same_server_required다.
- 원본과 구조화된 요구조건을 한 트랜잭션으로 저장하고 AUTO_INCREMENT ID를 반환한다. 원문 해석·보정·UPDATE/DELETE는 제공하지 않는다.
- 잘못된 형식·범위·빈 문자열·길이 초과·없는 FK를 거부하며 두 번째 INSERT 실패 시 첫 행도 롤백한다. 같은 내용의 재제출은 별도 Job이다.
- 상세·고객별 목록을 제공하고 신규 ID로 기존 매칭·대안·동의·배정을 이용한다. 인증·Flask UI·새 마이그레이션은 이번 범위 밖이다.
- [v0.4-1 검증 기록](v0.4-1-validation.md)을 수용 기준과 실제 시험 결과로 사용한다.

## F1·F2 동의 무결성 보강 (2026-11-18)

- 할당 이력(ACTIVE·COMPLETED·FAILED)이 있는 Job은 새 대안을 생성하거나 새로 수락할 수 없다. 기존 제안의 거절은 기록할 수 있고 기존 응답의 같은 의사 재요청은 기존 결과를 반환한다. 화면 버튼도 같은 정책으로 비활성화한다.
- Job당 수락은 한 번이며 철회·변경할 수 없다. 수락 대안의 배정이 실패하면 같은 대안 재시도, 원본 배정, 새 Job 등록 중 하나를 택한다. 같은 Job 안의 재협의는 지원하지 않는다.
- 스키마·제약·마이그레이션 변경은 없다. [F1 검증 기록](f1-allocation-history-validation.md)에 테스트와 실행 결과를 기록한다.
