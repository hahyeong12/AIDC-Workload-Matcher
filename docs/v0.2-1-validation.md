## 판단 구조

1. CLI에서 양의 BIGINT UNSIGNED Job ID를 검증한다. `001`과 `1`은 같은 ID다.
2. repositories에서 LEFT JOIN / WHERE와 매개변수화 SQL로 원본 요구조건과 모델을 조회한다.
3. JOIN / WHERE로 요청 모델의 개별 GPU, 장비 상태, 소속 서버와 운영 상태를 조회한다.
4. services에서 정확히 같은 모델 PK의 ONLINE + HEALTHY 장비만 집계한다.
5. 동일 서버 필수이면 서버별 최대 후보 수, 분산 허용이면 전체 후보 수로 판단한다. 한 서버만으로 분산 허용 요청을 충족해도 허용한다.
6. HARDWARE_FEASIBLE / HARDWARE_INSUFFICIENT, 사유 코드와 설명, 전체 장비·후보 목록 및 서버별 수량을 반환한다.

요청 모델 장비 부재는 MODEL_UNAVAILABLE, 총수량 부족은 QUANTITY_SHORTAGE, 동일 서버 부족은 SAME_SERVER_SHORTAGE다. 여러 사유가 함께 존재할 수 있다.
INVALID_JOB_ID / JOB_NOT_FOUND / MISSING_JOB_REQUIREMENT는 별도 오류다.
CLI는 같은 읽기 전용 REPEATABLE READ 스냅샷에서 조회하고 성공·실패 모두 롤백 후 연결을 닫는다. 저장소·서비스는 호출자의 트랜잭션을 종료하지 않는다.
개별 후보 목록과 서버별 집계의 기준을 공유하기 위해 Python에서 집계한다. 동일 데이터에 대한 별도 GROUP BY 쿼리는 추가하지 않았다.

결과는 하드웨어 수량·배치 조건에 대한 판단이다. 할당·예약 정보가 없으므로 실제 즉시 실행 가능 여부 또는 배정 확정을 의미하지 않는다.

## 테스트 결과

```powershell
# 작업 시작 시 기존 테스트 기준선
.\.venv\Scripts\python.exe -m pytest -q --run-mysql
# 82 passed

# 최종 로컬 검증 (실제 MySQL은 명시적 skip)
.\.venv\Scripts\python.exe -m pytest -q
# 107 passed, 51 skipped

# 최종 실제 MySQL 포함 전체 검증
.\.venv\Scripts\python.exe -m pytest -q --run-mysql
# 158 passed

.\.venv\Scripts\python.exe -m compileall -q app tests
.\.venv\Scripts\python.exe -m pip check
git diff --check
```

전체 테스트는 로컬 107개, 실제 MySQL 51개다. 신규 테스트 76개(로컬 52개, MySQL 24개)를 추가했고 기존 82개도 모두 통과했다. 최종 pytest 실행에 실패·오류·경고가 없다.
컴파일·의존성 검증과 Git 공백 검사도 통과했다.

통합 테스트는 실제 seed 결과, GPU/서버 상태 9조합, 모델 불일치, 동일 서버 필수·분산 허용, 없는 Job, 요구조건 누락, SELECT 전용 접근 및 판단 전후 데이터 보존을 포함한다.
임시 데이터는 기존 정책대로 TEST_MYSQL_* 전용 DB에 UUID 식별자로 삽입하고 롤백했다. 기존 seed 행은 수정·삭제하지 않았다.

## DB 보존 결과

신규 테스트 실행 전과 최종 테스트·CLI 실행 후, 별도 읽기 전용 연결로 개발·테스트 DB의 모든 행과 정의를 읽고 SHA-256 지문을 비교했다.
전체 행의 모든 컬럼(생성 시각 포함), 테이블 정의 및 트리거 정의가 전후 일치했다.

| 대상 | customers | gpu_models | servers | gpus | job_requests | job_requirements | 트리거 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 개발 DB 전후 | 3 | 2 | 4 | 10 | 5 | 5 | 4 |
| 테스트 DB 전후 | 3 | 2 | 4 | 10 | 5 | 5 | 4 |

개발 DB는 읽기 전용으로만 접근했다. 테스트 DB의 임시 행은 남지 않았다. 테이블·트리거를 생성·삭제·수정하거나 seed를 재적용하지 않았다.
테스트 DB의 InnoDB 자동 증가 카운터는 롤백으로 복구되지 않아 다음 번호에 간격이 생길 수 있다. 이 런타임 카운터는 기존 정책에 따라 테이블 정의 비교에서 제외했다.
검증용 로컬 지문과 CLI JSON은 Git에서 제외된 `.pytest-tmp/v021-before.json`, `v021-after.json`, `v021-cli.json`에 보관했다. 원본 행 덤프나 접속 정보는 기록하지 않았다.

## 향후 할당 관리 고려사항

- 정상 장비와 미할당 장비를 분리하고 활성 할당을 제외해 실제 가용 수량을 계산해야 한다.
- 배정 직전에 작업·서버·GPU 상태를 잠금 후 재검증해야 한다. 읽기 전용 스냅샷의 후보 목록만으로 배정을 확정하면 안 된다.
- 동일 GPU의 중복 활성 할당을 DB 제약과 일관된 잠금 순서로 막고, 교착상태·재시도를 처리해야 한다.
- 필요한 전 수량과 작업 상태를 하나의 트랜잭션으로 확정하고 오류·부족 시 전부 롤백해야 한다.
- 반복 배정 요청의 멱등성, 완료·실패 시 자원 해제, 할당 이력 보존이 필요하다.
- 고객이 승인한 원본 또는 대안과 실제 배정의 관계를 기록하고 승인된 조건을 배정 시 다시 검증해야 한다.
