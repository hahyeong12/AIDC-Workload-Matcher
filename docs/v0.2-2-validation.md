### 추가 테이블의 책임

기본 6개 테이블과 4개 트리거를 변경하지 않는다. [ERD와 전체 컬럼](../database/erd.md), [추가 SQL](../database/migrations/002_transactional_allocations.sql)이 기준이다.

- `allocations`: 자동 증가 배정 PK, 원본 Job FK, ACTIVE/COMPLETED/FAILED, UTC 배정·종료 시각. ACTIVE이면 종료 시각 NULL, 종료 상태이면 NOT NULL이며 배정 시각 이상이어야 한다.
- `active_job_request_id`: ACTIVE일 때만 Job ID, 종료 후 NULL인 STORED 생성 컬럼. UNIQUE로 같은 Job의 활성 할당을 최대 하나로 제한한다.
- `allocation_gpus`: `(allocation_id, gpu_id)` 복합 PK, 배정·GPU·배정 당시 서버 FK와 배정·반환 시각. 반환 시각은 배정 시각 이상이다.
- `active_gpu_id`: 반환 시각이 NULL인 동안 GPU ID, 반환 후 NULL인 STORED 생성 컬럼. UNIQUE로 같은 GPU의 미해제 할당을 최대 하나로 제한한다.
- 헤더와 자식 상태 일치, 원본의 정확한 수량과 동일 서버 조건은 서비스 트랜잭션에서 검증한다. 직접 SQL로 일부 상태만 바꾸는 작업은 지원하지 않는다.

### 마이그레이션 정책과 이번 실행

```powershell
.\.venv\Scripts\python.exe -m database.migrate
.\.venv\Scripts\python.exe -m database.migrate --test
```

개발 DB 결과는 `applied: false`, `pending_tables: [allocations, allocation_gpus]`였다. 테스트 DB는 `applied: false`, `pending_tables: []`였다. 둘 다 `original_data_preserved: true`였다.
이번에는 `--apply`를 실행하지 않았다. 이미 준비된 테스트 DB를 재마이그레이션하지 않고 개발 DB 적용은 별도 사용자 승인 이후로 남겼다.
기존 DB에 `schema.sql`·seed를 재실행하거나 DROP/TRUNCATE/기존 테이블 재생성을 하지 않는다. DDL은 암묵적으로 커밋되므로 부분 실패 시 자동 삭제하지 않고 검사 후 명시적 재개 정책을 따른다. [마이그레이션 안내](../database/migrations/README.md)를 참고한다.

## 코드 검토와 동시성 제어

기존 구현을 유지했다. 검토 대상은 `app/services/allocations.py`, `app/repositories/allocations.py`, CLI·결과 객체, 추가 SQL·마이그레이션·스키마 검사와 테스트다.

1. 배정·반환은 진행 중인 트랜잭션이 없는 전용 연결에서 READ COMMITTED로 시작한다.
2. `SELECT ... FOR UPDATE` 순서는 **GPU 모델 → Job → 원본 요구조건 → 서버 ID 오름차순 → GPU ID 오름차순 → 할당 헤더 → 할당-GPU 행**이다. 같은 모델의 배정·반환을 직렬화한다. 서로 다른 모델이 공유하는 서버도 ID 순서로 잠근다.
3. 잠금 전 읽기는 대상을 찾는 데 사용하고, 잠금 후 원본·장비·서버 상태와 점유를 재조회한다. READ COMMITTED로 잠금 대기 전 스냅샷에 가려진 다른 커밋을 놓치지 않는다.
4. ONLINE + HEALTHY 중 미점유 GPU를 선택한다. 동일 서버 조건을 유지하고 정확한 수량을 확보해야 INSERT한다. 부족·SQL 오류·반환 수량 불일치·잠금 오류이면 전체 롤백한다.
5. 정상 완료·실행 실패 시 모든 GPU 반환 시각과 헤더 종료 시각·상태를 같은 트랜잭션에 기록한다. 해제된 연결 행은 삭제하지 않는다.
6. 동일 Job의 반복 배정은 ACTIVE 또는 종료 결과를 반환한다. 같은 종료 상태의 반복 요청은 기존 시각을 보존하고, 다른 종료 상태로 변경하려 하면 충돌이다. 완료 후 같은 Job을 새로 실행하지 않는다.
7. 불일치한 직접 SQL 기록은 자동 복구하지 않는다. 미해제 자식 또는 ACTIVE 헤더가 있는 GPU를 보수적으로 점유로 처리하고 해당 할당 처리 시 무결성을 검사한다.

모델별 직렬화는 현재 규모의 정합성을 우선한 구현이다. 임의 외부 쓰기까지 advisory lock으로 차단하지는 않는다. 운영 변경 경로도 같은 잠금 정책을 따라야 한다. 자동 교착상태 재시도·장비 운영 API·명시적 Job 재실행은 이번 범위에 추가하지 않았다.
기존 `match_cli`와 하드웨어 서비스는 그대로 유지한다. 하드웨어 충족 결과는 점유를 반영한 가용성 또는 배정 확정과 구별한다.

### 실제 MySQL에서 확인한 사항

- 동일 Job의 ACTIVE 헤더 중복과 같은 GPU의 미해제 중복 INSERT가 errno 1062로 거부된다.
- 서로 다른 실제 연결에서 모델 잠금 대기를 확인한 뒤 경쟁 Job의 부족 판단, 동일 Job의 단일 할당·멱등 응답, 반환 후 대기 중 배정의 재사용, 동시 완료의 멱등성을 확인했다.
- 서비스 모델 잠금 없이도 GPU의 조건부 UNIQUE가 동시 직접 INSERT를 대기시키고 첫 커밋 후 두 번째를 1062로 거부했다.
- 수량 부족 시 헤더·자식에 부분 할당이 남지 않는다. 두 번째 GPU INSERT의 실제 FK 오류, GPU 반환 뒤 헤더의 실제 CHECK 오류 모두 이전 상태로 롤백된다.
- 정상 완료·실행 실패 후 모든 GPU가 반환되고, 다른 Job에서 재사용하며 이전 할당의 해제 기록이 보존된다.
- ONLINE/HEALTHY 9조합, 동일 서버·분산 배치, 원본 보존, PK/FK/UNIQUE/CHECK와 기존 하드웨어 매칭도 통과했다.

일반 배정 SQL 테스트는 삭제 금지 임시 Job을 보존하기 위해 외부 트랜잭션과 SAVEPOINT 외피를 사용한다. 동시성·CLI 6개는 실제 별도 연결의 START/COMMIT/ROLLBACK을 사용한다.
보완 검증으로 SAVEPOINT 외피 없이 실제 AllocationService 연결에서 다음 2건을 별도로 실행했다. 두 건은 pytest 통과 수에 더하지 않았다.

1. 첫 GPU INSERT 성공 후 두 번째 GPU FK 거부: 실제 외부 ROLLBACK으로 헤더·모든 자식이 사라지고 전체 지문이 일치했다.
2. 정상 배정을 커밋한 후 전 GPU 반환 UPDATE 성공, 헤더 CHECK 거부: 실제 외부 ROLLBACK으로 원래 ACTIVE 및 전 GPU 미해제 상태가 유지됐다. 등록한 임시 배정 ID만 정리한 뒤 전체 지문이 일치했다.

## 테스트 전후 보존과 기타 점검

독립 READ ONLY 스냅샷에서 `tests/mysql_audit.py`의 `snapshot`으로 모든 행(시각·생성 컬럼 포함), 정규화한 테이블 정의와 트리거 정의의 SHA-256 지문을 저장했다. 전체 스위트 후, MySQL 전용 실행 후, 추가 롤백 검증 후에 각각 비교해 모두 일치했다.
모든 seed 값도 전후 `seed.sql`과 대조했다. 논리 스키마 지문은 자동 증가 다음 번호를 제외한다. InnoDB 특성상 테스트 DB의 번호에는 간격이 생길 수 있으며 개발 DB에는 INSERT하지 않았다.

전체 snapshot을 `json.dumps(snapshot, sort_keys=True)`로 직렬화한 요약 SHA-256은 전후 다음과 같았다.

| DB | 전후 공통 SHA-256 |
| --- | --- |

일반 임시 행은 롤백했다. 커밋이 필요한 검증은 기존 정책대로 변경하지 않은 seed Job을 참조하는 임시 할당만 등록하고 정확한 소유 allocation_id의 자식·헤더만 정리했다. 원래 있던 행은 삭제하지 않았다. 이 정리는 테스트 전용이며 운영 서비스의 이력 삭제 기능은 없다.
JUnit XML, 읽기 전용 감사 JSON과 보완 검증용 일회성 스크립트는 Git 제외 경로 `.pytest-tmp/`에 보관했다. 접속 비밀정보·실제 데이터 덤프는 문서와 커밋에 포함하지 않았다.

`python -m compileall -q app database tests`, `python -m pip check`, 문서 로컬 링크 검사(39개 대상)와 `git diff --check`가 통과했다. VS Code 설정은 로컬 파일만 변경하며 커밋 대상은 README 및 검증 관련 문서다.

## 남은 작업

- 개발 DB의 추가 마이그레이션: **별도 사용자 승인 후** 점검 시간에 두 테이블만 추가하고 전후 보존을 검증한다. 현재 배정 CLI는 `--test`로 사용한다.
- 사용자가 VS Code UI에서 실제 선택된 인터프리터를 최종 확인한다. 기본 경로 설정과 터미널 표시만으로 선택 완료를 단정하지 않는다.
- 원본 요청·요구조건의 동일 트랜잭션 등록 서비스, 대안·고객 동의, 자동 실행 시뮬레이션·웹 UI는 후속 개발 범위다.
- 명시적 재실행 정책과 장비 운영 변경의 잠금 정책은 후속 설계로 남긴다.

이번 검증 완료는 기존 v0.2-2 코드와 테스트 DB 동작에 대한 완료이며 개발 DB 배포 또는 전체 제품 기능 완성을 뜻하지 않는다.
