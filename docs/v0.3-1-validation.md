## 생성 규칙과 실제 결과

기존 `evaluate_hardware`와 `evaluate_availability`, 모델·장비 조회 및 점유 제외 정책을 재사용한다. ONLINE 서버의 HEALTHY GPU 중 미해제 자식 또는 ACTIVE 헤더로 점유된 GPU를 제외한다. 같은 모델 PK만 사용한다.

1. 원본이 현재 AVAILABLE이면 ORIGINAL_AVAILABLE로 반환하고 불필요한 제안을 만들지 않는다.
2. 원본이 동일 서버 필수이고 한 서버에서 요청 수량을 확보할 수 없지만 전체 미할당 합계가 충분하면 **원본 수량을 유지하고 분산 배치를 허용**한다.
3. 원본 배치 조건을 유지하며 확보 가능한 최대 양의 수량을 원본보다 작게 제안한다. 동일 서버 필수이면 서버별 최대 수량, 분산 허용이면 전체 합계를 사용한다.
4. 원본과 같은 조건, 수량 증가, 수량 0, 다른 GPU 모델을 제안하지 않는다. 모든 제안 조건을 기존 가용성 평가기로 다시 검사한다.
5. 가용 GPU가 없으면 NO_FEASIBLE_ALTERNATIVES와 MODEL_UNAVAILABLE/AVAILABLE_QUANTITY_SHORTAGE 등 원본 부족 사유 및 NO_FREE_GPUS를 반환한다.

## 새 테이블과 관계

[003_workload_proposals.sql](../database/migrations/003_workload_proposals.sql)은 기존 8개 테이블·4개 트리거를 변경하지 않고 다음 2개만 추가한다. 전체 컬럼은 [ERD](../database/erd.md)를 따른다.

### job_proposals

- proposal_id AUTO_INCREMENT PK, 원본 Job·고객·GPU 모델 FK, 제안 수량·동일 서버 플래그·유형·이유·변경 JSON·주의사항·UTC 생성 시각.
- `(job_request_id, gpu_model_id, gpu_count, same_server_required)` UNIQUE로 같은 조건을 영구 중복 방지한다. 거절된 제안도 기존 ID·시각·내용·응답을 보존한다.
- `(proposal_id, job_request_id, customer_id)` UNIQUE는 응답의 복합 FK 부모다. customer_id는 서비스가 원본 Job에서 직접 읽어 기록한다.
- CHECK로 양의 수량, 0/1 배치, 허용 유형, DISTRIBUTED의 분산 플래그, 비어 있지 않은 이유·주의사항과 JSON 배열을 강제한다. 원본과의 모델·수량·배치 비교 및 실제 changes 일치는 서비스가 검증한다.

### proposal_responses

- response_id AUTO_INCREMENT PK, proposal_id·job_request_id·customer_id, ACCEPTED/REJECTED와 UTC 응답 시각.
- Proposal·Job·고객 세 컬럼의 복합 FK와 UNIQUE로 잘못된 조합 및 제안별 두 번째 응답을 막는다. proposal_id의 부모 튜플이 하나이므로 복합 UNIQUE만으로 한 제안에 최대 한 응답이다. 고객 FK도 별도로 둔다.
- `accepted_job_request_id`는 ACCEPTED일 때 Job ID, 거절이면 NULL인 STORED 생성 컬럼이다. UNIQUE로 Job당 수락을 최대 하나로 제한한다.
- 같은 Job의 다른 제안은 거절할 수 있으며 그 이력을 유지한다. Job별 응답 및 고객 FK 인덱스를 둔다.

기존 FK 9개에 신규 5개를 추가해 테스트 DB는 FK 14개다. 모두 RESTRICT이며 연쇄 삭제를 사용하지 않는다. [복합 FK](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html), [UNIQUE](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)의 실제 동작을 MySQL에서 확인했다.

## 응답 정책과 불변성 경계

서비스는 고객이 원본 Job의 소유자인지, 제안이 요청한 Job에 속하는지, 제안의 소유자 스냅샷이 원본과 같은지 검사한다. 다른 고객·Job 조합은 응답을 저장하지 않는다. 없는 제안은 PROPOSAL_NOT_FOUND다.
한 제안의 최초 ACCEPTED/REJECTED만 확정한다. 같은 의사는 response_id·responded_at을 보존하고 replayed=true로 재응답한다. 반대 의사는 PROPOSAL_CONFLICT다. 다른 제안의 추가 수락도 같은 충돌로 처리한다.
거절 후 다른 조건의 제안을 생성하거나 이미 다른 조건으로 제시된 제안에 응답할 수 있다. 기존 거절 기록이나 제안 내용을 덮어쓰지 않는다. 자원 변화로 H100 3개 제안 이후 H100 2개 제안이 생성되어도 이전 거절이 보존됨을 검증했다.

제안·응답 서비스는 INSERT와 조회만 제공하며 UPDATE/DELETE·수락 취소 API가 없다. 신규 테이블의 임의 직접 SQL 수정·삭제까지 DB 트리거로 차단한 것은 아니다. 운영 계정의 UPDATE/DELETE 제한이 필요하며 이번에 계정 권한이나 기존 트리거를 바꾸지 않았다. 원본 요청·요구조건은 기존 4개 트리거로 계속 보호한다.
확정 의사만 기록하며 반대 응답 시도 자체를 새 감사 행으로 저장하지 않는다. 이후 수락 변경 정책이 필요하면 기존 응답을 수정하는 대신 별도 사건 모델을 설계해야 한다.
CLI 고객 ID는 **업무 관계 검사이며 실제 로그인·인증이 아니다**. 결과 JSON의 authentication_notice에도 이를 명시한다.

## 트랜잭션과 동시성

쓰기에는 기존 `allocation_transaction`의 READ COMMITTED·전용 연결·전체 커밋/롤백을 재사용한다. 호출자가 이미 진행 중인 트랜잭션을 가진 연결은 거부한다.

- 생성: GPU 모델 → Job → 원본 요구조건 → 서버 ID 순 → GPU ID 순 → 제안. 잠금 후 기존 점유를 재확인하고 조건 키를 조회해 없을 때만 INSERT한다.
- 응답: GPU 모델 → Job → 원본 요구조건 → 제안 → 응답. 같은 Job의 의사를 직렬화한다. 잠금 대기 후 새로 커밋된 응답을 확인하고 재응답 또는 충돌을 결정한다.
- 생성 중 장비 행 잠금은 짧은 트랜잭션의 일관성 수단이다. 지속되는 예약이나 GPU 점유 행을 만들지 않는다.
- 단위 서비스 SQL은 SAVEPOINT 외피, 실제 동시성·CLI·외부 롤백 테스트는 별도 실제 연결의 START/COMMIT/ROLLBACK으로 검증했다.
- 시간 초과·DB 오류·업무 충돌이면 전체 롤백한다. 자동 무한 재시도나 부분 성공을 반환하지 않는다.

다른 제안에 대한 두 연결의 동시 수락에서 한 건만 커밋했다. 서비스 잠금을 거치지 않는 직접 INSERT도 첫 트랜잭션을 기다린 후 Job 수락 UNIQUE에서 errno 1062로 거부됐다. 같은 제안의 동시 동일 응답은 하나의 응답 ID·시각을 반환했다. 동시 거절/수락은 먼저 확정된 응답을 보존했다.
[MySQL 잠금 읽기](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)의 사용 범위를 따르며 모든 처리 경로에서 기존 배정 코드와 같은 모델 우선 순서를 유지한다.

## 제안·수락과 실제 배정

제안 생성·저장·수락·거절은 allocations/allocation_gpus INSERT, GPU/서버 상태 UPDATE, 기존 GPU 반환을 실행하지 않는다. 기존 AllocationService 구현은 변경하지 않았다.
제안 이후 다른 Job이 GPU를 점유해도 기존 제안을 현재 가용성을 보장하는 기록으로 바꾸지 않는다. 수락은 고객 의사 자체이므로 이때도 기록할 수 있으나 실제 배정은 수행하지 않는다. 기존 8개 테이블 지문이 동일한지 생성·응답 전후 비교했다.
`ProposalService.accepted(job_id)`의 AcceptedProposal은 basis_kind=ACCEPTED_PROPOSAL과 불변 proposal_id·response_id·원본 Job·수락 조건을 반환하는 읽기 인터페이스다. 인증이나 자원 확보를 의미하지 않는다.
