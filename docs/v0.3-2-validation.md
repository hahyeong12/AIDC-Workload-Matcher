# v0.3-2 실제 MySQL 검증 (2026-11-10, 노트북)

기준 커밋은 `e373e3a2f37ddd6b09c61f9b311ac5aa7b1a7446`이다. Windows / Python 3.14.6 / pytest 9.2.0 / MySQL 8.0.46, `use_pure=True` 및 TLS 연결에서 실행했다. 두 DB의 loopback 주소, 로컬 hostname과 기존 노트북 server UUID를 확인했다. 데스크톱 MySQL과 AIDC-Simulator에는 접근하지 않았다.

## 구현 및 설계

- AllocationService.allocate_proposal은 원본 소유자·Proposal의 Job/고객·정확한 ACCEPTED 응답·허용된 조건 변경을 잠금 안에서 확인한다. 현재 가용 GPU 전체 수량을 확보한 뒤 실제 배정·GPU 연결·근거를 함께 저장한다.
- 004는 allocation_bases 한 개만 추가한다. ORIGINAL / ACCEPTED_PROPOSAL과 Job·고객·Proposal·응답·모델·수량·동일 서버 플래그를 보존한다. 기존 allocations ALTER와 비교한 선택 이유 및 DB/서비스 검증 경계는 [설계 결정](decisions.md)에 기록했다.
- 생성·수락 시 예약하지 않는다. 같은 Job·같은 근거의 반복은 기존 ACTIVE/종료 결과를 반환하고 다른 근거는 충돌이다. 완료/실패는 기존 반환 기능을 재사용한다. 004 이전 할당은 ORIGINAL로 조회하며 백필하지 않는다.
- CLI에 allocate-proposal, detail, job-history를 추가하고 기존 allocate/history/complete/fail을 유지했다. 고객 ID 검사는 실제 인증이 아니다.

## 사전 검사·백업·마이그레이션

개발 8개·테스트 10개 테이블과 원본 트리거 각 4개, 모든 seed·행·정의가 완료된 노트북 환경의 지문과 일치함을 읽기 전용으로 확인했다. 할당·제안·응답 이력은 모두 0행이었다. 예상 밖 객체·루틴·이벤트도 없었다.

공식 mysqldump 8.0.46으로 테스트 DB를 `--single-transaction --no-tablespaces --set-gtid-purged=OFF` 등 옵션으로 백업했다. 비밀번호는 인자·문서·로그에 출력하지 않았다. 백업 파일은 Git 제외 경로 `database/backups/v0.3-2-laptop-20261110/test-before-004.sql`에만 보관한다.

- 크기: 21,630 bytes
- SHA-256: `bb7d0816d48215f7be80f1b94a66b03c3d3c1f6d828c9d77387b4fb1e79f1f54`
- 백업의 CREATE TABLE 10개와 원본 트리거 4개 포함 및 최종 해시 일치를 확인했다. 별도 인스턴스 복원 실험은 이번에 수행하지 않았다.

`database.basis_migrate --test` 사전 검사 후 `--test --apply`로 테스트 DB에만 CREATE TABLE 한 개를 실행했다. 생성 직후 nullable BIGINT의 `NULL`/`DEFAULT NULL` 표기 차이로 보수적 검사기가 중단했다. 같은 논리 정의인 것을 확인하고 새 SQL 자산 표기를 MySQL의 DEFAULT NULL 표현에 맞췄다. 기존 테이블을 ALTER/삭제/재생성하지 않았다. 재검사는 이미 완성된 11개 정의를 확인해 추가 DDL 없이 종료했다. 기존 10개 모든 값·정의와 트리거 지문은 적용 전후 같다.

기존 364개와 MySQL 134개를 유지했다. 신규 48개는 단위 20개·실제 MySQL 28개다. 실패·오류·skip·경고는 없다. 전체 및 MySQL 전용 JUnit XML의 testcase 수와 성공 상태를 별도로 확인했다. 로컬 JUnit·지문·summary는 같은 Git 제외 백업 디렉터리에 있다.

다음 항목을 실제 MySQL에서 검증했다.

- 동의 누락·거절·다른 고객/Job의 대안 거부, 적용 근거 불일치 거부.
- 수락 후 다른 Job이 GPU를 선점하면 재조회 결과 부족으로 실패하며 새 배정 행은 남지 않음. 반환 후 재시도는 성공.
- 두 번째 GPU INSERT, 근거 INSERT, 반환 헤더 갱신 오류 주입 시 전체 상태가 전후 동일. 외부 트랜잭션/SAVEPOINT 검사와 독립 연결의 실제 ROLLBACK을 구분해 검증.
- 두 연결의 실제 모델 잠금 대기를 Event로 확인. 같은 대안 요청은 한 할당으로 수렴, 다른 근거는 충돌, 경쟁 Job의 부족 요청은 부분 배정 없이 거부.
- 동시 완료는 같은 종료 시각과 기존 근거를 반환. 실제 MySQL의 ACTIVE Job/GPU UNIQUE는 직접 중복 INSERT도 거부.
- 새 근거의 CHECK/FK 및 응답 삭제 RESTRICT, 과거 원본 할당의 무백필 재사용·반환, 실제 하위 CLI 프로세스의 배정·근거·GPU/Job 이력·완료.

기존 불변 원본 Job을 테스트 목적으로 커밋/삭제하지 않았다. 단일 연결 시나리오는 외부 트랜잭션에서 롤백한다. 실제 커밋·동시성·CLI는 변경하지 않은 seed Job을 참조하는 테스트 소유 Proposal·응답·할당만 사용하고 등록한 정확한 ID의 근거→GPU 연결→할당→응답→Proposal 순으로 정리한다. 기존 행을 삭제하는 정리 API는 없다.
