기준 커밋: `b51f81a59936e9d7fd93909c18e3eb7adeea4abd`.
검증일: 2026-11-10 (Asia/Seoul).

## 등록·조회 사용법

프로젝트 루트에서 기존 `.env`와 `.venv`를 사용한다. 다음 등록 명령은 형식 예시이며
실행하면 테스트 DB에도 삭제 불가능한 원본이 영구 저장된다. 자동 검증은 아래의
pytest 명령으로 수행한다. 이번 개발 과정에서는 신규 원본을 실제 커밋하지 않았다.

```powershell
$python = '.\.venv\Scripts\python.exe'
# 고객 1과 GPU 모델 1이 이미 존재하는 전용 테스트 DB에 등록
$job = & $python -m app.job_cli --test register --customer-id 1 --title '신규 학습' --original-request 'H100 2개를 동일 서버에서 사용하고 싶습니다.' --gpu-model-id 1 --gpu-count 2 --same-server-required 1 | ConvertFrom-Json
& $python -m app.job_cli --test detail $job.job_request_id
& $python -m app.job_cli --test list 1
& $python -m app.match_cli $job.job_request_id --test
& $python -m app.allocation_cli --test available $job.job_request_id
# 현재 자원이 충분하면 원본 조건으로 배정
& $python -m app.allocation_cli --test allocate $job.job_request_id
```

등록 출력은 `{"job_request_id": <MySQL 생성 ID>}`다. 상세·목록은 원본 제목·문장,
고객·Job ID, 생성 시각(UTC), 모델 ID·수량·동일 서버 플래그를 포함한다.
존재하는 고객에게 Job이 없으면 빈 목록, 없는 고객이면 CUSTOMER_NOT_FOUND다.
Job 부재와 요구조건 누락은 JOB_NOT_FOUND / MISSING_JOB_REQUIREMENT로 구별한다.
고객별 목록은 Job ID 오름차순이며, 요구조건이 빠진 기존 Job이 있으면 무시하지 않고
MISSING_JOB_REQUIREMENT로 데이터 불완전성을 보고한다. 페이지 나누기는 후속 범위다.

`--test`는 최상위 옵션이며 서브명령 앞에 둔다. 생략하면 MYSQL_* 연결을 선택한다.
이번 작업의 실제 쓰기 검증은 TEST_MYSQL_*에서만 수행했고 개발 DB는 읽기만 했다.
TEST_MYSQL_DATABASE는 `_test`로 끝나며 개발 DB 이름과 달라야 한다.

## 저장과 원자성

- `app/job.py`: 입력 검증과 불변 상세 결과.
- `app/repositories/jobs.py`: 매개변수 바인딩을 사용하는 SELECT·INSERT만 제공.
- `app/services/jobs.py`: 기존 `allocation_transaction`을 재사용하는 등록 경계와 조회 서비스.
- `app/job_cli.py`: 등록, 상세, 고객별 목록과 JSON·종료 코드.

`job_requests`는 고객의 원본 문장·제목·소유자·생성 시각을 보존한다.
`job_requirements`는 매칭에 사용하는 명시적 모델·수량·동일 서버 조건을 보존한다.
공유 Job PK의 1:1 관계로 문장과 구조화된 조건을 연결한다. 자연어를 파싱하거나
문장과 조건이 다르다는 이유로 모델·수량·플래그를 바꾸지 않는다. 공백·줄바꿈도 보존한다.

등록 전 형식 검증 → READ COMMITTED BEGIN → 고객·모델 존재 검사 → 요청 INSERT →
연결의 `cursor.lastrowid`로 발급 ID 획득 → 같은 ID로 조건 INSERT → COMMIT 순서다.
FK는 사전 조회 이후 부모 삭제 경합까지 최종 보호한다. MAX(id)+1은 사용하지 않는다.
어느 단계에서든 실패하면 기존 경계에서 ROLLBACK한다. 기존 트랜잭션이 있는 연결은
TRANSACTION_IN_PROGRESS로 거부하며 호출자 트랜잭션을 커밋·롤백하지 않는다.
성공 반환은 COMMIT 호출이 성공한 뒤에만 한다. Repository는 직접 커밋하지 않는다.

동일 내용을 두 번 제출하면 별도 Job과 ID가 생성된다. 요청 멱등성 키·본문 기반 중복
추정·자동 재시도는 없다. 특히 COMMIT 중 네트워크 단절은 서버 커밋 여부가 불확실할 수
있다. 이 경우 오류를 반환하며, 고객별 목록 등으로 확인해야 한다. 재제출은 중복될 수 있다.

조회 CLI는 REPEATABLE READ 읽기 전용 스냅샷을 사용하고 종료 시 롤백한다.
Python에서 `JobService(connection).detail(id)` / `.list_for_customer(customer_id)`를
직접 호출할 때는 호출자가 조회 트랜잭션을 관리한다. 등록은 전용 연결을 사용한다.

## 검증·원본 보호·오류

| 항목 | 허용 조건 |
| --- | --- |
| customer_id / gpu_model_id | 양의 BIGINT UNSIGNED 정수 또는 ASCII 숫자 문자열, DB에 존재 |
| title | 공백만으로 이루어지지 않은 유효한 UTF-8 문자열, 최대 200자 |
| original_request | 공백만으로 이루어지지 않은 유효한 UTF-8 문자열, 최대 65,535바이트(TEXT) |
| gpu_count | bool·실수·문자열이 아닌 Python int, 1~2,147,483,647; CLI는 정수로 파싱 |
| same_server_required | 서비스: bool 또는 int 0/1; CLI: 명시적 0/1 |

ID의 bool·실수·부호·공백·비ASCII 숫자·SQL 조각은 거부한다. 잘라내기·공백 제거·기본값
대입·조건 추론을 하지 않는다. 장비 부족은 등록 거부 사유가 아니며 후속 매칭에서 판단한다.
모든 입력값은 `%s` 파라미터로만 전달한다. 기존 보호 트리거 4개를 그대로 유지하며
원본 UPDATE/DELETE 서비스는 추가하지 않았다. DB CHECK·FK도 그대로 유지한다.

CLI 종료 코드: 성공 0, 입력·대상·트랜잭션 소유권 오류 2, DB 설정·SQL·트랜잭션 오류 1.
입력 오류는 명시적 error/message JSON이다. DB 오류는 기존 DatabaseOperationError의
stage/object/errno/SQLSTATE만 노출하며 드라이버 원문·접속 비밀·고객 원문은 출력하지 않는다.
존재하지 않는 고객·모델은 CUSTOMER_NOT_FOUND / GPU_MODEL_NOT_FOUND로 구분한다.

## 매칭·대안·동의·배정 연결

새 ID는 기존 HardwareRepository·check_hardware와 가용성 조회에서 그대로 사용한다.
원본이 가용하면 AllocationService.allocate, 부족하면 ProposalService.generate → respond
→ AllocationService.allocate_proposal로 연결된다. 수락 후 자원을 다시 검사하는 기존 정책도 유지한다.
예를 들어 새 Job을 수량 2로 등록했는데 현재 GPU가 1개이면 수량 1 대안 생성·고객 수락·
ACCEPTED_PROPOSAL 근거의 배정이 가능하며 원본 수량 2는 보존된다.

```powershell
# 부족한 새 Job의 대안 경로; Job ID는 앞의 등록 결과 사용
$generated = & $python -m app.proposal_cli --test generate $job.job_request_id | ConvertFrom-Json
$proposalId = $generated.proposals[0].proposal_id
& $python -m app.proposal_cli --test accept $job.job_request_id $proposalId 1
& $python -m app.allocation_cli --test allocate-proposal $job.job_request_id --proposal-id $proposalId --customer-id 1
```

위 대안 예시는 PROPOSALS_AVAILABLE이며 대안이 존재할 때 사용한다. 가용 원본에는 불필요한
대안을 만들지 않는다. 실제 사용자 로그인·인증·접근 권한 검증은 이번 범위가 아니다.
전달된 customer_id의 존재·업무 관계 검사는 로그인한 사용자의 신원을 증명하지 않는다.

## 테스트 격리와 남은 제한

기존 테스트 파일·스키마·seed·마이그레이션·트리거 자산은 변경하지 않았다.
새 원본은 삭제할 수 없으므로 테스트 목적의 신규 Job COMMIT은 수행하지 않는다.
서비스·등록 CLI의 실제 SQL 성공 경로는 기존 RollbackEnvelope의 SAVEPOINT로 서비스
경계를 대체하고 외부 테스트 트랜잭션을 최종 롤백한다. 신규 Job의 원본·수락 대안 배정,
원문 보존·SQL Injection 입력·길이 경계·FK·4개 트리거·오류 원자성을 실제 MySQL에서 확인한다.

동시 등록은 두 독립 TEST_MYSQL_* 연결이 실제 BEGIN·INSERT로 발급한 서로 다른 ID와
정확한 부모·자식 연결을 확인한다. 두 트랜잭션이 모두 INSERT를 완료하도록 Barrier로
동기화한 다음 COMMIT 호출 경계에서 실제 ROLLBACK으로 대체한다. 실제 BEGIN 후
두 번째 INSERT의 CHECK 실패로 서비스 전체 ROLLBACK하는 경로도 별도 검증한다.
조회 CLI는 실제 하위 프로세스에서 실행한다. 등록 CLI의 실제 영구 커밋·새 프로세스 재조회는
원본 삭제 불가 정책 때문에 수행하지 않았으며, 실제 커밋 호출은 단위 테스트로 확인한다.
트리거 비활성화·원본 삭제 우회·DDL·권한 변경은 하지 않는다.

AUTO_INCREMENT는 롤백해도 소비되므로 다음 ID 증가·번호 공백은 남는다. 행·논리 테이블 정의·
트리거 지문은 실행 전후 비교하며 자동 증가 다음 값은 기존 정책대로 비교에서 제외한다.
Flask·인증·요청 멱등성 키·목록 페이지 나누기·자동 재시도는 후속 작업이다.
