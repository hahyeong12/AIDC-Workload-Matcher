# v0.4-2 Flask 웹 UI 검증

기준 커밋: `874702b6b522cde1af97d9fdb81cee07ea6bf370`.
검증일: 2026-11-10 (Asia/Seoul). Flask 3.1.3과 기존 `.venv`를 사용한다.

## 실행과 접속

저장소 루트의 Windows PowerShell에서 실행한다. 가상환경 활성화·Node 서버·새 패키지 설치는 필요하지 않다.
DB 연결 값은 기존 MYSQL_*와 `.env`를 사용하며 프로세스 환경변수를 우선한다.

```powershell
# 명시적인 읽기 전용 시연
$env:WEB_ENABLE_WRITES = '0'
.\.venv\Scripts\python.exe -B -m app.web
```

브라우저 주소는 **http://127.0.0.1:5000/** 이다. 종료는 Ctrl+C다.
기본 바인딩은 127.0.0.1, debug와 reloader는 비활성화다.
`app.create_app()` factory도 제공하지만 외부 바인딩·debug 실행·프록시 배포는 이 MVP의 지원 범위가 아니다.
서버를 시작해도 DB 초기화·seed 재입력·마이그레이션을 하지 않는다.

## 화면별 기능

| 화면 / 주소 | 동작 |
| --- | --- |
| `/` | 시연 고객 선택, 전체·정상·가용 GPU, 모델별 수량, 서버 상태, 고객별 Job과 진행 상태 |
| `/jobs/new?customer_id=1` | 고객·제목·원문·GPU 모델·수량·동일 서버 여부 입력 |
| POST `/jobs/preview` | 서버 측 검증과 FK 존재 확인 후 등록 전 확인 화면; DB 쓰기 없음 |
| POST `/jobs` | 확인표를 한 번 소비하고 기존 JobService.register 호출; 성공 시 상세로 303 이동 |
| `/jobs/<id>?customer_id=1` | 원문과 명시적 조건, 하드웨어 검사·현재 가용성·부족 이유, 대안·할당 근거·반환 이력 |
| `/jobs/<id>/proposals/<proposal_id>?customer_id=1` | 원본·제안 조건 비교, 수량 축소·분산 허용 변경, 제안 이유·주의사항·응답 기록 |
| POST `/jobs/<id>/actions/<action>` | generate / accept / reject / allocate / allocate-proposal / complete / fail |

고객 선택은 시연용이다. 선택한 고객과 Job, Job과 Proposal·할당의 업무 관계를 검사하지만
로그인·실제 인증·사용자 간 보안 권한 분리를 제공하지 않는다. 누구나 로컬에서 다른 시연 고객을 선택할 수 있다.

정상 GPU는 HEALTHY 장비다. 가용 GPU는 ONLINE 서버의 HEALTHY 장비 중 기존 가용성 서비스가
미점유로 판단한 장비다. 따라서 유지보수 서버의 정상 장비는 정상 수량에는 포함되지만 가용에서는 제외된다.
진행 상태는 등록 완료 → 대안 검토 → 동의 기록 → 배정 중 → 완료/실패·반환으로 표시한다.
대안은 원본을 바꾸지 않는다. 수락만으로 예약·배정하지 않으며 별도의 배정 요청에서 다시 검사한다.
할당 이력은 GPU ID·배정 당시 서버 ID·배정/반환 시각(UTC)과 ORIGINAL/ACCEPTED_PROPOSAL 근거,
Proposal·응답 ID 및 적용 조건을 표시한다. 기존 근거 없는 과거 원본 배정도 별도로 표시한다.

원본 수정·삭제, GPU 학습 실행, 예약·과금·시간 예측, 실제 인증은 구현하지 않았다.

## 계층과 트랜잭션

`app/web.py`는 HTTP 입력·CSRF·시연 관계 검사·화면 이동을 담당한다.
`app/services/workspace.py`는 읽기 화면 자료를 조합하고 `app/repositories/workspace.py`는
고객·GPU 모델·서버·현재 DB 이름을 매개변수화 SELECT로 조회한다.
JobService, check_hardware, get_availability, ProposalService, AllocationService의 판단·쓰기 로직은 변경하지 않는다.
가용성 집계도 기존 evaluate_availability를 사용하며 라우트에서 GPU 선택·조건 변경·배정 SQL을 구현하지 않는다.

factory 생성 시 DB에 연결하지 않는다. 요청에서 처음 필요한 순간 한 연결을 열어 `g`에 저장한다.
스키마·대상 DB 검사와 조회는 REPEATABLE READ / readonly / consistent_snapshot 트랜잭션에서 실행하고 롤백한다.
쓰기 전 사전 소유 관계 조회도 롤백으로 종료한 뒤 기존 서비스가 전용 연결에서 READ COMMITTED BEGIN·COMMIT/ROLLBACK을 수행한다.
미종료 읽기 트랜잭션을 서비스 쓰기 경계로 가져가지 않는다.
요청 종료 시 성공·실패와 관계없이 롤백을 시도하고, 롤백 실패에도 finally에서 연결을 닫는다.

GET은 조회만 수행한다. DB 상태를 변경하는 동작은 POST뿐이다. POST preview는 입력을 검증하고
프로세스 메모리에 확인표만 저장하며 DB를 변경하지 않는다. 고객 선택과 CSRF는 서명된 세션 쿠키에 저장한다.

## 웹 쓰기 안전장치

웹은 항상 MYSQL_* 연결을 사용하며 TEST_MYSQL_*로 자동 전환하지 않는다.
DB의 실제 SELECT DATABASE() 결과, 기존 검사 도구의 테이블·InnoDB·CHECK/FK·정의 일치와
원본 보호 트리거 4개를 요청마다 읽기 전용으로 검사한다. 누락·부분·예상 밖 정의는 안전한 오류로 중단한다.

다음 조건이 **모두** 충족돼야 웹 쓰기가 가능하다.

1. 프로세스 설정 `WEB_ENABLE_WRITES=1`을 명시한다. 기본은 0이다.
2. `WEB_WRITE_DATABASE`가 실제 연결 DB 이름과 정확히 일치한다.
3. 정상 v0.3-2 스키마, 11개 테이블 및 정상 원본 보호 트리거 4개가 있다.
4. 실제 DB 이름이 `_test`로 끝나지 않고 TEST_MYSQL_DATABASE와도 일치하지 않는다.
5. localhost 요청, 정상 Host, 유효한 세션 CSRF 및 대상 관계 검사를 통과한다.

8개(v0.2-2)·10개(v0.3-1) 정상 스키마는 원본·장비·가용성·기존 할당 이력 조회만 제공한다.
대안·응답·신규 근거 기능이 가능하다고 표시하지 않으며, 웹 쓰기를 전부 차단한다.
따라서 현재 개발 DB에서 명시적 쓰기 설정만 추가해도 등록·배정 버튼은 활성화되지 않는다.

아래는 **별도 승인·백업·003·004 적용 및 검증이 끝난 뒤에만** 사용하는 실행 형식이다.
이번 작업에서는 이 설정으로 개발 DB에 쓰지 않았다. TEST_MYSQL_*를 복사하거나 테스트 DB를 지정해 시연하지 않는다.

```powershell
$env:WEB_ENABLE_WRITES = '1'
$env:WEB_WRITE_DATABASE = 'aidc_workload_matcher'
.\.venv\Scripts\python.exe -B -m app.web
# 시연 종료 후 쓰기 비활성화; 실행 중인 서버도 종료·재시작해야 반영됨
$env:WEB_ENABLE_WRITES = '0'
Remove-Item Env:WEB_WRITE_DATABASE
```

WEB_SECRET_KEY는 선택적 세션 비밀키다. 미설정/빈 값이면 시작할 때 무작위 키를 생성해 서버 재시작 시 기존 세션·폼이 무효화된다.
로컬 환경변수나 Git 제외 `.env`에서만 보관하고 실제 값을 문서·터미널 출력·커밋에 넣지 않는다.
서버의 쓰기 설정은 시작 시 읽으므로 환경변수 변경만으로 실행 중 서버가 바뀌지 않는다.

## 입력·CSRF·XSS·충돌

- 모든 POST는 세션에 연결된 무작위 CSRF 토큰과 상수 시간 비교를 수행한다. 실패하면 DB 연결 전에 거부한다.
- 등록 검증은 v0.4-1 validate_registration을 재사용한다. 제목 200자, 원문 UTF-8 65,535바이트,
  양의 정수 수량과 ID, 명시적 0/1을 검사하며 원문 공백·줄바꿈은 보존한다.
- Jinja2 HTML 자동 이스케이프를 사용한다. 고객 원문을 safe/Markup/innerHTML로 처리하지 않는다.
- CSP는 외부 자원·inline script/style·프레임·base 변경을 제한한다. 외부 CDN·폰트·분석 도구는 없다.
- 정상 Host와 loopback 원격 주소만 허용하며 전달 헤더로 원격 주소를 신뢰하지 않는다. 쿠키는 HttpOnly·SameSite=Strict다.
  localhost HTTP 시연이므로 HTTPS 배포나 인증 보안을 주장하지 않는다.
- 요청 크기와 폼 메모리를 제한하고 응답에는 no-store·nosniff를 적용한다.
- 등록 확인표는 세션에 연결된 프로세스 메모리의 한 번 쓰는 표다. 15분 만료·최대 256개이며 DB 쓰기 전에 잠금으로 소비한다.
  같은 표 재제출은 409다. JavaScript의 중복 클릭 억제는 보조이며 서버 표가 중복 등록을 제어한다.
- 별도 확인표로 같은 내용을 새로 제출하면 별도 Job이다. DB 멱등성 키는 추가하지 않는다.
  COMMIT 응답 유실 등 결과 불확실 오류에서도 표를 자동 재사용하지 않는다. 이력을 확인하고 새로 작성해야 한다.
- 기존 대안 응답·배정·반환 반복은 기존 서비스의 멱등성·충돌 정책을 유지한다. 반대 응답·다른 근거·다른 종료 상태는 409다.
- 입력 오류 400, 다른 고객 403, 대상 부재 404, 자원 부족·충돌 409, DB·스키마/예상 밖 오류 503을 제공한다.
  화면에 비밀정보·SQL·스택트레이스를 표시하지 않는다. 로그도 안전한 오류 유형 또는 기존 DatabaseOperationError 진단만 남긴다.

## 개발 DB 003·004 적용을 위한 후속 절차

이번 구현은 마이그레이션 도구·SQL·개발 DB를 변경하지 않았다. 다음은 별도 작업이다.

1. 웹 서버·쓰기를 중지하고 정확한 MYSQL_* 대상, 8개 테이블·트리거 4개, 기존 행·정의 지문을 확인한다.
   `python -m database.proposal_migrate`는 읽기 점검만 가능하며 개발 --apply는 기존 CLI가 거부한다.
2. 적용할 DB·003 후 10개/004 후 11개 예상 객체·실행 계정·백업·복구 계획을 제시해 별도 사용자 승인을 받는다.
3. 공식 mysqldump로 일관된 전체 백업(기존 데이터·정의·트리거, 필요 시 루틴·이벤트)을 Git 제외
   `database/backups/`에 저장한다. 접속 비밀번호를 인자에 적지 않고 해시·크기·복원 가능성을 확인한다.
4. 승인된 관리자가 기존 `003_workload_proposals.sql` → 검증 → `004_allocation_bases.sql` 순서로 적용하거나,
   개발 대상 승인 경로를 제공하는 후속 도구 작업을 한다. 현재 CLI의 `--test`로 개발 DB를 우회하지 않는다.
   스키마 초기화·seed 재입력·기존 객체 삭제·자동 재시작은 하지 않는다.
5. DDL은 암묵적으로 커밋된다. 중간 실패 시 삭제/재생성하지 않고 부분 상태를 보존·진단한다.
   기존 8개 정의·행·트리거 지문 유지, 새 3개 테이블 정의, 전체 11개 구성과 서비스 읽기 호환성을 확인한다.
6. 현재 테스트 DB는 자동 검증 전용으로 유지한다. 개발/별도 승인 시연 DB에서만 웹 쓰기 대상 설정을 명시한다.
   시연의 새 원본은 영구 데이터이므로 삭제 불가 정책을 수용한 뒤 등록한다.

## 검증 격리와 제한

Flask 테스트 클라이언트와 실제 MySQL을 함께 사용한다. 신규 웹 원본을 테스트에서 실제 COMMIT하지 않는다.
기존 외부 롤백 정책을 따르는 WebRollbackConnection이 요청 조회와 서비스 트랜잭션을 SAVEPOINT로 감싼다.
서비스 COMMIT은 SAVEPOINT 해제이며 fixture의 실제 외부 트랜잭션은 마지막에 롤백한다.
웹 테스트 예외는 TESTING=True, 명시적 WEB_TEST_ROLLBACK_ONLY=True, 주입 연결의
web_rollback_only=True가 모두 있어야 한다. 이 설정은 환경변수·웹 요청으로 활성화되지 않으며 일반 서버는 사용하지 않는다.
테스트 어댑터는 조회 트랜잭션도 SAVEPOINT로 대체하므로 실제 MySQL readonly 플래그 자체는 정상 개발 DB GET 요청으로 별도 확인한다.

기존 서비스 동시성·실제 커밋 테스트는 그대로 유지했다. 새 웹 성공 경로의 영구 COMMIT·다른 프로세스 재조회는
원본 삭제 불가 정책 때문에 수행하지 않았다. 트리거를 끄거나 원본 삭제를 우회하지 않는다.
AUTO_INCREMENT 번호는 롤백해도 소비된다. 행·논리 정의·트리거 지문은 비교하되 다음 자동 증가 값은 제외한다.

현재는 단일 프로세스 로컬 MVP다. 확인표·세션을 여러 서버에서 공유하지 않고 페이지 나누기·실시간 갱신은 제공하지 않는다.
상태 갱신은 새로고침한다. 스키마를 요청마다 검사하는 비용이 있으며 대규모 운영 성능은 검증하지 않았다.
동시 DDL·스키마 변경과 웹 시연을 함께 수행하지 않는다.

오류 롤백이다. GPU 수량 축소뿐 아니라 새 Job의 분산 배치 대안 수락 후 서로 다른 두 서버에 배정하는 경로도 확인했다.

Chrome headless로 실제 localhost 서버의 대시보드(1440px·390px), Job 상세, 등록 폼과 등록 전 확인 화면을
렌더링하고 스크린샷을 검토했다. 390px에서 문서 너비도 390px이며 표는 자체 가로 스크롤을 제공한다.
브라우저 JavaScript 예외는 0건이고, 확인 화면의 영구 등록 버튼이 비활성화된 것을 확인했다.
실제 브라우저는 개발 DB 읽기·preview만 사용했으며 등록·배정 POST는 실행하지 않았다.
웹 쓰기 성공 경로는 외부 롤백으로 격리한 Flask/MySQL 테스트에서 검증했다.
검증용 서버·브라우저는 종료했다. JUnit XML·전후 지문·스크린샷·로컬 QA 도구는 Git 제외 `.pytest-tmp/`에만 있다.

| DB | 최종 스키마 | 테이블 | 원본 보호 트리거 |
| --- | --- | --- | --- |
| 개발 | v0.2-2 | 8 | 4 |
| 테스트 | v0.3-2 | 11 | 4 |

별도 읽기 전용 연결의 사전/사후 검사에서 두 DB의 모든 행·논리 테이블 정의·트리거 지문이 일치했다.
양쪽 customers=3, gpu_models=2, servers=4, gpus=10, job_requests=5, job_requirements=5를 유지했고
allocations·allocation_gpus는 각 0행이다. 테스트 DB의 job_proposals·proposal_responses·allocation_bases도 각 0행이다.
테스트 신규 원본은 남지 않았다. 테스트 DB의 AUTO_INCREMENT 소비·번호 공백은 롤백되지 않는다.
개발 DB의 003·004를 적용하지 않았고 schema·seed·트리거·마이그레이션·과거 테스트·기존 비즈니스 서비스는 변경하지 않았다.
실제 `.env`·`.venv`·인증정보·백업·다른 저장소는 변경하거나 커밋하지 않았다. `.env.example`에는 비밀값 없는 웹 설정만 추가했다.
